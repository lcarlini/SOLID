SolidFlow

Five design rules that keep software easy to change. Shown here with the SolidFlow pricing engine — one quote, many policies, no tangled conditionals.

Walk the principles View the code

One request. A flowing pipeline.

In SolidFlow, a quote does not grow by stuffing more if branches into one class. It flows through small policies that each answer one question.

Request Customer + cart
Catalog Resolve products
QuoteService Orchestrate
Policies Volume · Premium · …
PriceQuote Total + adjustments

SOLID, simply.

Each letter is one rule. Each rule has a tiny SolidFlow example. Scroll with the flow — nothing fancy, just clear software habits.

S O L I D
S

Single Responsibility

One job per piece

A class should have one reason to change.

If pricing rules, HTTP wiring, and product lookup all lived in one file, every small change would risk breaking everything else.

In SolidFlow

QuoteService only builds quotes. InMemoryProductCatalog only finds products. VolumePricingPolicy only decides volume discounts.

// three reasons to change → three types
class QuoteService { … }
class VolumePricingPolicy { … }
class InMemoryProductCatalog { … }
O

Open / Closed

Extend, don’t rewrite

Open for new behavior. Closed for edits to working code.

Add a campaign discount by writing a new policy — leave QuoteService alone.

In SolidFlow

New rules implement IPricingPolicy and register in DI. The pipeline picks them up automatically.

class CampaignPolicy : IPricingPolicy
{
  PriceAdjustment? Evaluate(…) { … }
}
 
services.AddSingleton<IPricingPolicy, CampaignPolicy>();
L

Liskov Substitution

Swap without surprises

Any policy can replace another and the quote still makes sense.

Every policy returns an adjustment or null. None secretly mutate the cart or throw for “not applicable.”

In SolidFlow

PremiumCustomerPolicy and VolumePricingPolicy honor the same contract — the service loops them the same way.

foreach (var policy in _policies)
{
  var adjustment = policy.Evaluate(context, total);
  // same shape, any policy
}
I

Interface Segregation

Small contracts, not fat ones

Depend only on the methods you actually use.

Callers ask for a quote service or a catalog — not one mega-interface that mixes pricing, shipping, and inventory.

In SolidFlow

Focused surfaces: IQuoteService, IPricingPolicy, IProductCatalog.

interface IQuoteService
{ PriceQuote CreateQuote(…); }
 
interface IProductCatalog
{ GetAll(); FindBySku(…); }
D

Dependency Inversion

Depend on ideas, not details

High-level flow should not hard-wire concrete classes.

The API composes abstractions at startup. Endpoints talk to IQuoteService, not new QuoteService(…).

In SolidFlow

Composition root in Program.cs wires policies and services. Core stays free of ASP.NET details.

AddSingleton<IPricingPolicy, VolumePricingPolicy>();
AddSingleton<IPricingPolicy, PremiumCustomerPolicy>();
AddSingleton<IQuoteService, QuoteService>();

Change prices. Keep the flow.
